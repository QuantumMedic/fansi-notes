# 04｜內容資料模型、SOP 串接與每週更新

> 本文件是「不再重複貼文」的主要規格。對話中的 SOP、GitHub、Spotify、Instagram、Vocus **沒有天然同步機制**；要依本文件實作明確、可核准、可追蹤的同步操作。

## 1. 一個作品 ID，對應多個呈現版本

- `work_id`：不可變的穩定 ID，例如 `three-idiots`；不可依標題改名自動重建。
- `slug`：網站 URL 用，可變更但需留下 301 轉址或對應映射；`work_id` 才是穩定關聯主鍵。
- `written_master`：IG／Vocus 共用的**正式書面母稿**；網站完整文章只從這份核准版取文。
- `podcast_master`：獨立的錄音逐字稿，**預設私人**，不放進公開 GitHub。
- `instagram_pages`：IG 分頁或圖卡輸出，可公開時才放到對外素材庫；與 `written_master` 的文字內容仍需 SOP 驗收。
- `podcast_episode`：可獨立正式標題、封面、RSS GUID、Spotify URL、介紹與日期；與 `work_id` 關聯。
- `platform_urls`：`instagram_url`、`vocus_url`、`spotify_episode_url` 各可為空；不強制某作品一定有所有媒介。

## 2. 建議資料欄位（Codex 應實作 schema 驗證）

| 分組 | 欄位 | 說明 |
|---|---|---|
| 身分 | `work_id`, `slug`, `title`, `subtitle`, `public_author_name` | 作者名稱僅使用核准公開版 |
| 分類 | `content_type`, `topics[]`, `keywords[]`, `related_work_ids[]` | 作品系列擇一；topics[0] 為主要、topics[1] 為選填次要，至多兩個不同主題 |
| 書面 | `written_master`, `summary`, `sources[]`, `cover_image`, `interior_images[]` | 僅核准公開的內容進公開 repo |
| 媒體 | `podcast_title`, `podcast_description`, `spotify_guid`, `spotify_episode_url`, `instagram_url`, `vocus_url`, `canva_design_refs` | `canva_design_refs` 可私人保存，避免外露編輯資訊 |
| 出版 | `site_publish_at`, `site_published_at`, `site_status`, `approved_revision` | 時區一致為 Asia/Taipei，內部 ISO 8601 含時區 |
| 作品集 | `book_status`, `book_cover`, `publisher`, `publication_year`, `purchase_urls[]`, `reading_order`, `public_excerpt` | 缺官方資料不得憑空補寫 |
| 搜尋 | `tags`, `search_description`, `social_image`, `language` | 預設 `zh-TW` |

**狀態請分兩條軌道：**

1. **創作流程（私人）**：未開始 → 草稿 → 作者待確認 → 書面母稿已定稿 → 視覺待驗收 → 完成 SOP。  
2. **網站發布（公開）**：私人待發布 → 作者明確核准網站公開 → 已送出公開內容 → 網站已上線／需修訂。

不能因為「SOP 完成」就推論「網站可公開」。作者必須另外給出明確網站公開授權。

## 4. 每週操作：從一份定稿到網站

### A｜在 ChatGPT 完成 SOP（不自動寫入網站）
1. 作者獨立確認 Podcast 長版母稿與 IG／Vocus 書面母稿。  
2. 製作 IG 圖卡與 Podcast 封面，確認 Canva 各自可編輯。  
3. 確認 `work_id`、作品系列、主要主題、選填次要主題、Podcast GUID 關聯、公開摘要、關聯作品（可空）、可公開視覺素材。
4. 更新單篇狀態卡；此時作品可以維持「私人待發布」。  

### B｜作者下達「同步網站」且核准公開後
1. 助理／Codex 取得這篇**核准的書面母稿與必要公開素材**。  
2. 驗證分類、日期、連結、圖片授權、重複 ID、路徑合法性，檢查 metadata 與正文完整性。  
3. 建立／更新 GitHub 公開站點的單篇內容紀錄（預設透過 PR／差異檢查；作者可明確授權直接合併，但不能偷跳核准）。  
4. PR 合併進 `main` 後 GitHub Actions 自動建站；首頁最新文章、類型列表、主題頁、搜尋索引、相關作品一起更新，不需逐頁操作。  
5. 檢查線上網址、圖片、文章全文、導覽、公開時間。  

**注意：** 因 `QuantumMedic/fansi-notes` 是公開 repo，**不可在發布日前把待發表全文提交到公開分支**；即使網站依 `site_publish_at` 暫時隱藏，Git 歷史仍公開。若未來要提前排五週，需第二個私人來源（私有 repo／私有 CMS）與正式授權後的安全發布工作流程。

### C｜作者自行發布 IG／Vocus
- 各貼一次已發布單篇的正式網址（或在未來私有管理介面填一次）。
- 助理／Codex 透過 `work_id` 精準更新對應平台 URL；頁面上的「觀看 IG」與「閱讀 Vocus」自動出現。
- 不下載 IG 圖卡再 OCR 當母稿；網站文章永遠以核准書面定稿為準。
- 不在這一階段登入或代替作者發布外部平台。

### D｜Spotify RSS 自動發現單集
1. 作者提供《凡思聲》**公開 RSS feed URL**（由 Spotify for Creators 後台取得）。
2. GitHub Actions 使用 `schedule`（例如每天一次）、`workflow_dispatch`（手動重跑）在**建站時**抓取 RSS，轉成經驗證的公開 episode metadata；不把原始 RSS（可能含 email）直接存進 GitHub。
3. 已發布的 RSS 單集可自動出現在 `/podcast/`；若 Spotify episode URL 尚未取得，先提供 RSS 的合法外部入口或不顯示 Spotify 播放器，不能猜造 Spotify URL。
4. 若有人工核准的 `episode_guid -> work_id` 映射，該單集才會顯示在相應文章頁；若無映射，顯示「待關聯」於私人維護報告中，**禁止用標題模糊相似就自動掛錯文章**。
5. RSS 讀取失敗：不覆蓋現有網站為空列表，記錄錯誤並允許手動重新觸發；排程不保證分秒準確。

**Spotify feed 細節：** RSS 的 `guid`、`title`、`pubDate`、`enclosure` 與 `link` 不必然等於 Spotify episode ID。應支援作者後補 `spotify_episode_url` 或可靠的合法解析方式；播放器使用官方 Embed，不自行下載／託管音訊。異名篇名如《三個傻瓜》的 IG 與 Podcast 標題，必須按穩定 ID 關聯。

## 5. 搜尋、最新列表、分類與推薦的更新方式

- **新增一篇核准公開文章**：建站系統依 metadata 自動建立文章頁、最新文章列表與類型／主題索引。
- **更改分類**：只修改該作品 metadata 一次，所有分類頁下一次建站一起更新。
- **更改書面正文**：使用作者重新核准的版本，記錄 revision 與日期；必要時更新其他平台仍由作者處理。
- **更改標題與 slug**：保留原 URL 轉址，避免舊 IG／Google 連結失效。
- **發表一集 Podcast**：RSS 同步後新增單集頁；關聯到文章需 GUID 映射確認；不假裝全部自動關聯。
- **發布 IG／Vocus 後**：各輸入一次正式 URL，作品頁下一次建站出現外連。
- **精選文章**：與日期無關，由作者指定；不能因新文推出而自動清空策展。
- **相關作品**：先用明確 `related_work_ids`，標題、主題只是輔助提示。

## 6. 重要限制與長期擴充

- GitHub 連接器可供在這裡**接到明確同步指令後**編輯 repo，但 Codex 或 GitHub 不會一直監看 ChatGPT 私人對話。沒有額外程式／觸發器，就不存在「SOP 一完成即無條件自動上站」。
- v1 每週最少人工步驟：① 在這裡核准網站公開；② 自己發布外部平台；③ IG/Vocus 各提供一次網址；④ RSS 異名配對首次確認一次（後續 GUID 固定）。
- v2 可考慮私有 Fansi Studio 管理台、由授權私人來源預排網站文章、Meta 專業帳號媒體 API 自動發現；不需在第一版先建完整後端。

## 7. 安全與稽核

所有內容更新須記錄 `work_id`、版本、核准者與時間。絕不可把未發布全文、作者私人狀態卡、個人聯絡地址、API 金鑰、Podcast 錄音原檔或未核准書封放入公開 Git repo。必須能追查某篇網站文章使用的正式母稿版本，並能撤回下架與修復錯誤連結。

## 8. M3 已確認的系列與分類制度

分類字典唯一來源：`src/data/taxonomy.json`。`content_type` 是作品系列，不是媒介：fansiwei＝凡思維、longform＝深度內容、special＝特別篇。《凡思聲》是 Podcast 節目，收錄所有系列；小說與出版仍獨立管理。

九大主題：心理與行為、醫學與生命、科學與科技、哲學與人生、歷史與社會、書籍與文學、影視與動畫、信仰與神學、個人與創作。持久識別使用字典的 slug；改顯示名稱只改字典，不改每篇紀錄。新增主題也只在字典增加一筆，schema、下拉選單和主題路由一起產生。若改 slug，需一併遷移參照與舊網址，不應把改顯示名稱誤當改 ID。

`topics` 第一項是必填主要主題，第二項是選填次要主題，必須不同且最多兩項。`keywords` 是獨立自由關鍵字陣列，不受九大類限制，也參與搜尋。

### 一次修改的資料來源

- 有網站文章的作品：分類只存文章 Markdown frontmatter（`content_type`、`topics`、`keywords`），沿用既有 `work_id`；文章核准與來源驗證不變。新增或更新一筆文章後，建置即更新首頁、文章／系列／主題／搜尋／相關作品，不改各頁程式。
- Podcast-only：人工分類存 `src/data/podcast-classifications.json`，以真實 GUID 識別，並給穩定 `work_id`。這些是公開 RSS 的分類 metadata，沒有網站文章正文。
- `src/data/podcast-work-map.json` 僅存作者核准的 GUID → work_id 關聯，禁止從相似標題自動推論。Podcast-only 後來補網站全文時，沿用它的 work_id，補上明確核准映射，不新建另一個作品 ID。
- 建置的共用作品目錄按 work_id 合併文章與 Podcast，因此系列／主題頁只顯示一張作品卡，可同時有閱讀與收聽入口。RSS 標題可以和文章不同。

### 分類優先順序與狀態

1. 有核准的文章關聯：以作品文章分類為準，日後只改文章一次即可更新所有關聯單集。
2. 無核准關聯、有獨立分類：保留獨立人工分類。`confirmed` 必須有 `reviewed_by` 與 `reviewed_at`。
3. `proposed` 是待審核建議，只供本階段預覽，畫面明確標示「分類建議・待審核」，不轉成 confirmed。
4. 完全沒有分類：仍出現在全部 Podcast，顯示「分類待確認」，不因缺少系列或主題而移除。

初始 25 筆全部是 proposed：凡思維 5、深度內容 17、特別篇 3。可在 `/review/classifications/` 審閱。資料以 GUID 持久保存，排序只用於顯示。這批建議的程式提交、預覽或作者提供初始建議，都不等於最終分類核准或網站部署授權。

### RSS 與人工資料隔離

RSS 只寫 `podcast.json` 的公開展示欄位，從不寫分類表或作品映射表，既有 Spotify／Apple 單集連結保留。讀取失敗保留舊快取。每日工作目前為唯讀審閱 artifact，不回寫分支、不部署；這取代前文對未來部署流程的概述。本 PR 不改部署權限。

本文件與 SOP 增補更新只發生在 GitHub；不代表 ChatGPT 專案設定、專案附件或私人創作 SOP 已被自動修改。


## 正式建置與本機分類審閱（2026-11-13）

- `npm run dev` 才會註冊 `/review/classifications/`，顯示 proposed 建議與審閱入口；請僅在本機使用開發伺服器。
- `npm run build` 與 `npm run preview` 不提供審閱路由或入口。審閱頁不進入靜態輸出、公開導覽、搜尋資料或可供網站地圖收錄的路由；不是只靠 noindex 隱藏。
- 正式建置只採用已確認的 Podcast 分類（含已核准作品關聯所沿用的文章分類）。獨立單集的 proposed 系列、主題、關鍵字不進入公開分類與搜尋；單集仍顯示於全部 Podcast，標示「分類待確認」。合成文章仍是明確標示的測試資料。
- 25 筆 GUID 建議資料原樣保留，不自動核准或刪除。確認後才填入 confirmed、reviewed_by、reviewed_at，重新建置後同步更新各頁。
- 此限制針對網站產物；依作者要求保留的分類資料與程式碼仍存在 GitHub Repository，這不是具登入權限的私人後台。
- 未合併、未部署，維持 M3。GitHub 文件更新不代表 ChatGPT 專案設定或附件已自動修改。
