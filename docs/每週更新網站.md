# 每週更新網站

網站已上線；目前狀態與線上版本見 [CURRENT_STATE](CURRENT_STATE.md)。本頁是每週操作的唯一入口，沿用創作 SOP 的作者確認制度，不改創作流程。通常週二發 Podcast、週三發 IG／Vocus，再整合更新網站一次；日期可以調整，不要求每個平台分別部署。

## 作者每週只需做的事

1. 在原創作 SOP 確認 **IG／Vocus 共用書面母稿**、版本、固定 `work_id`、系列、主要主題與最多一個次要主題、核准圖片。Podcast 稿與書面稿分開；本流程不改寫文章。
2. 自行發布各平台後，讓本週私人交接檔可被 Codex 讀取，再說：「同步網站；本週平台已發布，授權將指定版本同步並公開網站。」這句可一併授權該次內容 PR 合併及 full／index 發布；只有「同步網站」時，預設做到驗證、預覽與 PR，不推定發布授權。未確認的分類、圖片或 GUID 對應仍須作者確認，不能靠標題猜。
3. 查看變更摘要，於 GitHub 的 `github-pages` Environment 親自核准發布（現行 prepare、deploy 各一次）。原有審核與回退保護不省略。作者已於 2026-11-17 明確授權正式索引；後續正式更新保持 index，不因內容更新恢復 noindex。

工程核對、RSS 備料、資料寫入、討論串清冊、建置、CI、PR 和經授權的發布準備可由 Codex 接續完成。這不是每週自動爬文／自動公開的承諾，也不需要每週重跑全站視覺驗收。

## 私人母稿如何真正交接

**ChatGPT 私人對話、附件與狀態卡，不因存在於專案內就能被本機 Codex 讀取。** 本輪搜尋已連接 Drive 的相關資料夾／母稿未取得可用入口；不假稱已有雲端自動同步。

本機已準備 repository 外的私人收件目錄：`~/.config/fansi-notes/weekly-inbox/`（目錄權限 0700）。每個作品放一個資料夾，內含：

- `master.md`：從創作 SOP 匯出的核准共用書面母稿，UTF-8 Markdown，保留原文、結尾與段落。不得用 Vocus 重爬、IG OCR 或 Podcast 逐字稿取代。
- `handoff.json`：由定稿端依 [交接樣板](../examples/weekly-handoff.template.json) 匯出。樣板刻意未授權且不可直接匯入，分類也只是格式示意，必須換成作者已確認值。記錄母稿版本、檔案 SHA256、work_id、分類、可公開核准者稱呼、核准時間、實際發布日期、署名、摘要來源、公開平台 URL。不要放私人 Email、對話全文或不相關狀態卡。
- 如需圖片：只附已核准素材與穩定段落位置／alt／圖說；使用現有詳頁封面與內文圖片機制，無圖可留空。本工具不搜尋、下載或自動授權圖片。

**一次匯出檔案，不用重新貼全文。** 若創作端有已授權的檔案／Drive 工具，可直接寫入雙方可讀取的私人位置；Codex 先使用已可取得的檔案與固定檔案 ID。否則作者把創作端產生的兩個檔案下載到上述資料夾，或在 Codex 附上檔案位置即可。這個匯出／下載是尚無跨產品存取權時不可省略的資料交接，不是要求重寫或重貼。未公開定稿一直留在私人目錄，不能先提交公開分支再隱藏。

`master.sha256` 對應檔案實際 bytes；`master.revision` 必須等於 `metadata.approved_revision`。定稿端可計算 SHA256；Codex 也可在核對作者指定版本後計算，不能用新 hash 掩蓋改稿。核准公開後才設定三個旗標 `public_authorization`、`platforms_published`、`metadata.website_approved` 為 true。

平台網址放 `metadata.platform_urls.instagram_url`／`vocus_url`；多貼文用 `related_instagram_urls`。Vocus／IG 僅核對公開網址及發布狀態，不當作未來新作的全文來源。沒有版本就省略欄位，不造網址。圖片權利與稿件公開授權分開。

Podcast 連結已經由作者確認時，加上 `podcast: {"guid":"實際 RSS GUID","approved":true}`；未確認就省略，單集仍可在全部 Podcast 展示。不使用標題相似度配對。新文章沒有 Podcast 也能匯入。既有作品只補平台或 GUID 時沿用同一 `work_id`／slug，帶入 `expected_article_sha256`（目前完整 Markdown 檔 hash）；原文不同或版本不符會拒絕，正文修訂另走作者審稿。

## Codex 的一次更新操作

以下變數都是本機路徑，不能將私人目錄或原稿上傳公開 artifact。先 fetch、核對 main、開獨立分支，確認沒有並行變更；保持原有 work_id，不重新分類。

```sh
umask 077
# 指向已存在的本週私人資料夾，不能直接使用尚未核准的樣板。
WEEKLY_INPUT="$HOME/.config/fansi-notes/weekly-inbox/本週作品"
# 一次讀公開 RSS 到私人備料；不更動 repository 的 podcast.json。
npm run sync:podcast -- --output "$WEEKLY_INPUT/podcast-preview.json"
# 先驗證，不寫入 repository；失敗不輸出母稿正文。
node scripts/weekly-sync.mjs "$WEEKLY_INPUT/handoff.json" --rss "$WEEKLY_INPUT/podcast-preview.json" --allow-public
# 已有本次公開授權才產生一個全新、repo 外的變更目錄；拒絕覆寫既有目錄。
node scripts/weekly-sync.mjs "$WEEKLY_INPUT/handoff.json" --rss "$WEEKLY_INPUT/podcast-preview.json" --allow-public --output "$WEEKLY_INPUT/staged-v1"
```

`--allow-public` 是工程端明確操作，不能取代作者授權。所有欄位、原文 hash、版本、重複 ID／slug、GUID 存在與已核准映射一致性通過後才產生檔案。預設不寫 repo，不合併、不部署。正式資料錯誤先修私人交接檔；不編造缺欄。

Codex 檢查 staged 的逐檔差異後，只套用列出的檔案至新分支。新作通常是一篇 Markdown、RSS 資料、核准 GUID 映射及 `written-master-provenance.json` 版本紀錄。公開紀錄只留來源類型、版本、hash 與可公開核准資訊，不包含私人母稿路徑。分類沿用文章 metadata，配對 Podcast 在建置時沿用同一分類；不另外複製第二份作品分類。原有平台與人工分類不由 RSS 覆寫。

```sh
npm run sync:threads
node scripts/sync-comment-threads.mjs --check
npm run check
npm run build
npm test
```

首頁最新四篇、系列、主題、搜尋、相關作品、文章／Podcast 互連與留言清冊會依資料重新建置；熱門值未知維持 null，不捏造人氣。精準驗收新作品與新連結，原歷史本文 hash 與配對保障保留。補入已公開很久的 Podcast 關聯時，要先檢查是否已有獨立 Podcast 討論串留言：若有，先提出保留留言的遷移方案，不直接改 alias 導致舊留言失聯；一般週三首次一起發布書音版本不需此遷移。

## RSS 每日備料，不等於發布

現有 `sync-podcast.yml` 每日台灣時間約 06:23 執行（GitHub 可能延遲），也可手動執行。只有 contents:read，產生 `podcast-review` artifact；不推送、開 PR、合併或部署。週二發表後可等下一次備料，週三整合一次即可。artifact 過期或執行尚未完成時，Codex 可執行上方私人 `--output` 命令取得目前公開 RSS。

以 GUID 更新標題、介紹、日期、封面；保留既有單集 slug、Spotify／Apple 及官方單集網址，RSS 缺少舊集不刪除。人工分類、GUID 映射與人氣資料均不由 RSS 寫入。新集沒有分類仍可正常展示。新集若缺 Spotify／Apple 直達 URL，只用可核實的官方資訊，不能猜產品 ID。

排程使用 RSS／交接精準測試與 check/build 驗證新備料；歷史全站測試保留在正式內容 PR 的 CI。沒有為自動備料新增寫入權限。

## 合併後的一次正式更新（必須已有授權）

沿用 [M6 工具與回退](review/m6/README.md) 及 `release.yml`，不新建第二套發布流程：

1. 內容 PR 全綠、作者已明確授權該次合併與公開，才 merge commit；等待 main CI。記下前次正式 SHA、兩個 Worker 版本及既有私人備份位置。
2. 討論串允許清冊被編入公開／管理 Worker。**新作發布不只上傳 Pages**：以同一核准提交及現有私人 production 設定，必要時更新本專案兩個 Worker 的清冊；保持 Access、AUD、精確來源與既有開關，不重建 D1、不搬入合成留言。先比較清冊，再有限核對新 thread 及原 thread，失敗即停在發布前。這項遠端更新也包含在明確的「同步並公開網站」授權內；只有工程／PR 授權時不得執行。
3. 使用既有已驗證私人設定執行 `node scripts/launch/service-release.mjs PRIVATE_PRODUCTION.json NEW_PRIVATE_MANIFEST.json`，為目標 main SHA 重新產生完整服務 manifest。沿用真實證據，不補假 true。經現有權限更新 `github-pages` 的 `RELEASE_SERVICES_JSON` secret；不輸出秘密或管理網址。缺權限時集中回報，不能為方便改成 services=off。
4. 手動 `release.yml`：目標完整 SHA、`PUBLISH_STATIC_PRODUCTION`、services=`full`、`ENABLE_VERIFIED_PRODUCTION_SERVICES`、indexing=`index`、indexing_confirmation=`AUTHORIZE_INDEXING`。這沿用作者已確認的正式索引決策，不改成 noindex；workflow 的保守預設不是目前正式站的選項。作者依序核准 Environment，Codex 等待結果後核對正式新頁、跨平台連結與新討論串。一般 push／PR 不會發布。
5. 發布失敗保留舊站；必要時以同一手動流程發布前次已驗證 SHA，Worker 使用各自記錄版本回退；不刪留言資料庫。既有單服務故障處理與 D1 備份工具不變。
